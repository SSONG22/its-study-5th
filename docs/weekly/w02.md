2026-10-12

> 이 시점의 계획은 AWS Lambda 배포였다. 3주차에 로컬 우선으로 순서를 바꿨다.
> 아래 내용은 당시 기록 그대로 둔다.

## 1. 이번 주에 한 일

### 참여 이유 정리

- 회사에서 LLM 을 쓰고는 있음. 크롤링으로 모은 데이터를 분류하고 정제하는 용도
- 이 쓰임은 조건이 단순함
  - 입력이 크롤링 데이터라 양과 형태가 정해져 있음
  - 배치로 돌려서 지연이 사용자 경험에 영향을 주지 않음
  - 처리량이 예측 가능해 비용 변동이 없음
  - 요청이 몰리지 않아 동시 처리 문제가 없음
- 성능이 변수가 되지 않는 조건에서만 써본 상태
- 이번에는 반대 조건을 선택. 입력 길이가 매번 변하고, 지연이 체감되고, 요청이 몰릴 수 있는 구조

### 주제 선정 기준 수립

문제: 사용자가 없으면 응답 시간 분포도 동시 처리 한계도 잴 수 없음.
트래픽이 쌓이길 기다리면 8주가 지나감.

→ 순서를 뒤집음. "무엇을 만들까"가 아니라 "무엇을 만들면 측정할 수 있을까"부터 정함.

기준 6개

1. 입력 크기 변동 폭이 커야 함 — 입력이 비슷하면 중앙값과 상위값이 같게 나옴
2. 단계가 여러 개여야 함 — 호출 하나뿐이면 병목 분석이 "모델이 느리다"로 끝남
3. 응답 시간 제한에 부딪힐 여지가 있어야 함
4. 재사용(캐싱) 지점이 있어야 함
5. 모델을 나눠 쓸 여지가 있어야 함
6. 질문 묶음을 재현 가능하게 만들 수 있어야 함

6번이 트래픽 문제의 해법.

### 후보 비교

| 후보 | 강점 | 탈락 이유 |
|---|---|---|
| 섀도잉 발음 코치 | 측정 축 최대. 음성 변환 과금, 저장소 전송, 요청 크기 제한 등 모델 밖 요인 다수 | 오디오 처리라 8주에 혼자 어려움. 매번 녹음해야 해서 실사용이 안 쌓임 |
| 기사 맞춤 리딩 교재 | 단계 최다. 수준별 재사용 설계가 복잡 | 크롤링 의존도가 높아 외부 변수 많음 |
| 영작문 첨삭 | 구현 가장 쉬움 | 측정 재료가 8주를 못 채움 |
| **영어 회화 롤플레이** | 아래 | **선택** |

### 선택 이유

- 바꾸는 값이 명확함. 대화 주고받은 횟수
- 횟수가 쌓이면 이전 대화를 매번 다시 보내야 해서 보낸 글자가 선형으로 증가
- 입력 변동을 설계로 만들 수 있음 (깊이 1 / 3 / 5 / 10)
- 증가를 억제하는 방법이 여러 개이고 각각 장단점이 다름
- 매 회 앞부분이 반복되는 구조라 재사용 효과를 가장 뚜렷하게 볼 수 있음
- 영어 학습이라는 본래 목적이 있어 직접 쓰게 됨 → 실사용 기록이 일부 쌓임

### 측정 설계

**원칙 4개**

- 질문 묶음은 한 번 만들고 고정. 바꾸면 이전 결과와 비교가 깨짐
- 한 번에 설정 하나만 변경
- 조건 변경은 코드가 아니라 배포 설정으로
- 측정할 때마다 버전 표시를 남기고 결과 파일과 짝지음

**질문 묶음** — 상황 20개 × 깊이 4종 = 80건. 생성 후 고정

**요청마다 기록할 항목** — 조건(방식·모델·횟수), 글자 수(보냄·재사용·받음), 걸린 시간

**방법과 가설**

| 방법 | 기대 | 대가 |
|---|---|---|
| 전체 전달 | 맥락 유지 | 보낸 글자 선형 증가 |
| 최근 N회만 | 보낸 글자 일정 | 앞부분 손실 |
| 오래된 건 요약 | 맥락 유지 + 절감 | 요약 호출 비용 추가 |
| 재사용(캐싱) | 보낸 글자 과금 절감 | 적중 조건 제약 |
| 모델 나눠 쓰기 | 비용 절감 | 품질 저하 |
| 서버 메모리 증설 | 지연 감소 | 사용 요금 증가 |

## 5. 다음 주 할 일

### 작업

1. AWS 계정과 예산 알림 설정
2. 배포해서 응답하는 주소 확보
3. 80건으로 첫 측정 — 숫자가 나오는지 확인
4. 깊이 1과 10의 보낸 글자 차이 실측

### 예상

- 깊이가 깊어질수록 보낸 글자가 선형으로 증가할 것
- 재사용이 걸리면 보낸 글자 과금이 크게 줄 것
- 최근 N회만 보내면 보낸 글자가 일정해져 비용이 크게 줄 것
- 오래된 걸 요약하면 맥락을 유지하면서 글자를 줄일 수 있을 것
- 모르는 것을 물으면 모델이 되물을 것
