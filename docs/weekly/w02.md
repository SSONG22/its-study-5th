## 1. 무엇을 고민했나

### 출발점

LLM을 더 깊이 다뤄볼 기회가 필요해서 참여했다.

회사에서 LLM을 쓰고 있긴 하다. 크롤링으로 모은 데이터를 분류하고 정제하는 용도다.
다만 이 쓰임은 조건이 꽤 편하다.

- 입력이 크롤링 데이터라 **양과 형태가 정해져 있다**
- 배치로 돌리니 **지연이 사용자 체감에 영향을 주지 않는다**
- 처리량이 예측 가능해서 **비용이 튀지 않는다**
- 사용자 요청이 몰리는 일이 없으니 **동시성 문제가 생기지 않는다**

즉 LLM을 쓰긴 했지만, **성능이 문제가 되지 않는 조건에서만** 써봤다.
지연도 비용도 동시성도 전부 상수인 환경이었다.

그래서 이번에는 일부러 반대 조건을 골랐다.
입력 길이가 요청마다 변하고, 지연이 사용자 체감에 바로 걸리고, 동시 요청이 몰릴 수 있는 구조.
LLM을 더 깊이 다루려면 그 조건 안에 들어가봐야 한다고 봤다.

### 주제 선정 기준

주제를 고르면서 가장 걸렸던 건 트래픽이었다.
사용자가 없으면 p95도 동시성도 잴 수가 없는데, 그렇다고 트래픽이 쌓이길 기다리면 8주가 그냥 간다.
8주 안에 실사용 트래픽을 모으는 건 어렵다고 봤다.

그래서 **트래픽이 없어도 측정이 성립하는 서비스**를 찾는 쪽으로 방향을 잡았다.
"무엇을 만들까"가 아니라 **"무엇을 만들면 잴 수 있을까"부터 역으로** 정했다.

기준 6가지를 먼저 세우고 아이디어를 걸렀다.

1. 입력 크기 변동 폭이 커야 한다 — 입력이 다 비슷하면 p50과 p95가 똑같이 나온다
2. 단계가 여러 개여야 한다 — LLM 호출 하나뿐이면 병목이 "OpenAI가 느림"으로 끝난다
3. API Gateway 29초 한계에 부딪힐 여지 — 안 부딪히면 비동기·스트리밍 전환 실험 명분이 없다
4. 캐시 지점이 있어야 한다
5. 모델 라우팅 여지가 있어야 한다
6. **입력 세트를 재현 가능하게 만들 수 있어야 한다** ← 트래픽 문제의 해법

### 후보와 탈락 이유

| 후보 | 강점 | 탈락 이유 |
|---|---|---|
| 영어 섀도잉 발음 코치 | 측정 축 최대. STT 분당 과금, TTS 문자당 과금, S3 전송, payload 6MB 제한 등 **LLM 바깥 병목이 쏟아짐** | 오디오 처리라 8주에 혼자는 빠듯. 매번 녹음해야 해서 실사용도 안 쌓임 |
| 기사 → 맞춤 리딩 교재 | 단계 최다. 사용자 레벨별 캐시 키 설계가 흥미로움 | 크롤링 의존이 커서 외부 변수가 많음 |
| 영작문 첨삭 | 구현 가장 쉬움 | 측정 재료가 8주를 못 버팀 |
| **영어 회화 롤플레이** | 아래 | **선택** |

### 왜 회화 롤플레이인가

**독립변수가 하나 명확하게 있다. 대화 턴 수다.**

턴이 쌓이면 히스토리를 매번 다시 보내야 하니 입력 토큰이 선형으로 증가한다.
비용과 지연이 턴 수에 비례해 올라가는 구조다.

- 입력 변동을 설계로 만들 수 있다 (턴깊이 1 / 3 / 5 / 10)
- 그 증가를 누르는 손잡이가 여러 개고, 서로 트레이드오프가 다르다
- **프롬프트 캐싱 효과를 가장 극적으로 볼 수 있다** — 매 턴 앞부분이 그대로 반복되니까
- 영어 공부라는 본래 목적이 있어 내가 실제로 쓴다 → 합성 부하 외에 실사용 로그도 조금 쌓인다

## 2. 만들 서비스

상황을 고르고 영어로 대화하는 멀티턴 롤플레이 API.
시나리오 20개 — 카페 주문, 공항 체크인, 면접, 컴플레인 대응 등.

```
클라이언트 → API Gateway → Lambda (nodejs22) → OpenAI
                              ↓
                        CloudWatch Logs (kind="bench" JSON 한 줄)
```

세션 상태를 서버에 두지 않고 클라이언트가 history를 매번 보낸다.
구현은 단순하지만 턴이 깊어질수록 요청 본문과 입력 토큰이 함께 커진다.
**이 구조 자체가 측정 대상이다.**

## 3. 성능 측정을 어떻게 할 것인가

### 원칙 4가지

1. **입력 세트는 한 번 만들고 고정한다.** 바꾸면 이전 결과와 비교가 깨진다
2. **한 주에 손잡이 하나만 바꾼다.** 둘을 동시에 바꾸면 무엇이 효과였는지 알 수 없다
3. **조건 변경은 코드가 아니라 배포 파라미터로 한다.** 같은 커밋에서 조건만 달리 배포해야 비교가 깨끗하다
4. **측정할 때마다 git tag를 남기고 결과 CSV와 1:1로 묶는다**

### 트래픽 문제를 어떻게 풀 것인가

실사용자를 기다리지 않고 **고정 입력 세트 80건**을 만들었다.

```
시나리오 20개 × 턴깊이 1 / 3 / 5 / 10 = 80건
```

턴깊이가 독립변수다. 매 측정마다 같은 세트를 같은 순서로 돌린다.
실트래픽보다 오히려 전후 비교가 깨끗하다. 이미 생성해서 레포에 넣어뒀다.

### 요청 한 건당 기록하는 것

```json
{
  "kind": "bench",
  "coldStart": true,
  "historyTurns": 10,
  "historyStrategy": "full",
  "inputTokens": 1842,
  "cachedTokens": 1536,
  "outputTokens": 64,
  "llmLatencyMs": 1230,
  "totalLatencyMs": 1310,
  "memoryMB": 512,
  "model": "gpt-4.1-mini"
}
```

`cachedTokens`가 이 프로젝트의 핵심 지표다.

### 손잡이와 가설

| 손잡이 | 기대 | 대가 |
|---|---|---|
| 히스토리 전체 전달 (full) | 맥락 유지 | 토큰 선형 증가 |
| 최근 N턴만 (window) | 토큰 상수 수렴 | 맥락 손실 |
| 오래된 턴 요약 압축 (summary) | 토큰 절감 + 맥락 유지 | 요약 호출 비용 추가 |
| 프롬프트 캐싱 | 입력 토큰 과금 절감 | 적중 조건 제약 |
| 모델 라우팅 | 비용 절감 | 품질 저하 |
| Lambda 메모리 증설 | 지연 감소 | GB-초 비용 증가 |

전부 코드가 아니라 SAM Parameter로 빼뒀다. `sam deploy --parameter-overrides` 로만 조건을 바꾼다.

### 8주 뒤에 답하고 싶은 질문

- 10턴 쌓이면 1턴 대비 요청당 비용이 **몇 배**가 되나
- 프롬프트 캐싱은 그 증가를 **몇 %** 눌러주나
- window와 summary 중 **비용 대비 효율**이 좋은 쪽은
- 동시 요청을 올리면 **어디서 먼저 무너지나** — Lambda 스로틀인가, OpenAI 429인가, 타임아웃인가
