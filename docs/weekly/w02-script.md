2026-10-12 (월) 22:00 · 디스코드 · 15분

## 0:00 시작 (30초)

안녕하세요, 안송이입니다.

오늘은 제가 뭘 만들지, 그리고 그걸 어떻게 측정할지 두 가지를 말씀드리려고 합니다.
주제 정하는 데 시간을 꽤 썼는데, **그 고민 과정이 측정 계획이랑 직접 연결돼 있어서**
거기부터 시작하겠습니다.

## 0:30 출발점 (2분)

저는 LLM을 좀 더 깊이 다뤄보고 싶어서 이 스터디에 들어왔습니다.

회사에서 LLM을 쓰고 있긴 합니다. 크롤링으로 모은 데이터를 분류하고 정제하는 용도예요.
그런데 이걸 하면서 느낀 게, 이 쓰임은 조건이 참 편하다는 거였습니다.

입력이 크롤링 데이터니까 양이랑 형태가 거의 정해져 있고요.
배치로 돌리니까 좀 느려도 아무도 신경 안 씁니다.
처리량이 예측되니까 비용도 안 튀고요.
사용자 요청이 몰릴 일이 없으니까 동시성 문제도 안 생깁니다.

> 여기서 한 박자 쉬기

정리하면 LLM을 쓰긴 썼는데, **성능이 문제가 안 되는 조건에서만** 써본 겁니다.
지연이든 비용이든 동시성이든, 저한테는 전부 상수인 환경이었어요.

그래서 이번에는 일부러 반대 조건을 골랐습니다.
입력 길이가 요청마다 변하고, 지연이 사용자한테 바로 체감되고, 동시 요청이 몰릴 수 있는 구조요.
LLM을 더 깊이 알려면 그 조건 안에 한번 들어가봐야겠다고 생각했습니다.

## 2:30 주제 선정 기준 (2분)

그러고 나서 뭘 만들지 고민했는데, 제일 걸렸던 게 **트래픽**이었습니다.

사용자가 없으면 p95를 잴 수가 없잖아요. 동시성도 마찬가지고요.
근데 트래픽이 쌓이길 기다리면 8주가 그냥 갑니다.
8주 안에 실사용자를 모으는 건 현실적으로 어렵다고 봤어요.

그래서 생각을 뒤집었습니다.
**트래픽이 없어도 측정이 성립하는 서비스를 찾자.**
"뭘 만들까"가 아니라 **"뭘 만들면 잴 수 있을까"부터** 정한 거죠.

기준을 여섯 개 세웠는데, 다 읽지는 않고 중요한 것만 말씀드리면요.

첫째, **입력 크기 변동 폭이 커야 합니다.**
입력이 다 비슷하면 p50이랑 p95가 똑같이 나와요. 그럼 잴 게 없습니다.

둘째, **단계가 여러 개여야 합니다.**
LLM 호출 하나뿐이면 병목 분석이 "OpenAI가 느리네"로 끝나버려요.

그리고 여섯 번째가 핵심인데, **입력 세트를 재현 가능하게 만들 수 있어야 한다**는 겁니다.
아까 말한 트래픽 문제의 해법이에요. 뒤에서 다시 말씀드리겠습니다.

## 4:30 후보와 탈락 이유 (1분 30초)

이 기준으로 영어 학습 쪽 후보 네 개를 걸렀습니다.

제일 아쉬웠던 건 **섀도잉 발음 코치**예요. 측정 관점에서는 제일 좋았습니다.
음성이 들어오는 순간 LLM 바깥 문제가 쏟아지거든요.
STT는 분당 과금, TTS는 문자당 과금, S3 전송 비용 붙고,
Lambda 동기 호출 payload 6MB 제한에도 걸립니다. 비용 분해가 토큰에서 안 끝나요.

근데 오디오 처리라 8주에 혼자 하기엔 빠듯하다고 봤고,
매번 녹음해야 해서 제가 실제로 안 쓸 것 같았습니다.

**기사 맞춤 리딩 교재**는 단계가 제일 많았는데 크롤링 의존이 커서 외부 변수가 많았고,
**영작문 첨삭**은 만들기는 제일 쉬운데 측정 재료가 8주를 못 버팁니다.

그래서 **회화 롤플레이**로 정했습니다.

---

## 6:00 왜 회화 롤플레이인가 (1분 30초)

이걸 고른 이유는 하나입니다. **독립변수가 명확해서요. 대화 턴 수입니다.**

멀티턴 대화는 턴이 쌓이면 이전 히스토리를 매번 다시 보내야 합니다.
그러면 입력 토큰이 선형으로 늘어나요.
**비용이랑 지연이 턴 수에 비례해서 올라가는 구조**입니다.

이게 왜 좋냐면요.

입력 변동을 제가 설계로 만들 수 있습니다. 턴깊이를 1, 3, 5, 10으로 놓으면 되니까요.
그리고 이 증가를 누르는 손잡이가 여러 개인데 서로 트레이드오프가 다릅니다.

특히 **프롬프트 캐싱 효과를 제일 극적으로 볼 수 있어요.**
매 턴마다 앞부분이 그대로 반복되니까 캐시가 잘 먹는 구조거든요.

마지막으로 영어 공부라는 본래 목적이 있어서 제가 실제로 씁니다.
그럼 합성 부하 말고 실사용 로그도 조금은 쌓이겠죠.

## 7:30 만들 서비스 (1분 30초)

> 구조도 화면 공유

서비스 자체는 단순합니다. 상황 고르고 영어로 대화하는 API예요.
시나리오 20개 준비했습니다. 카페 주문, 공항 체크인, 면접, 컴플레인 대응 같은 것들이요.

구조는 API Gateway, Lambda, OpenAI. CloudWatch에 측정 로그를 남깁니다.

여기서 한 가지 의도적으로 정한 게 있는데요.
**세션 상태를 서버에 두지 않았습니다.** 클라이언트가 history를 매번 통째로 보내요.

구현은 단순한데 턴이 깊어질수록 요청 본문이랑 입력 토큰이 같이 커집니다.
비효율적으로 보이죠. 근데 일부러 이렇게 뒀습니다.
**이 구조 자체가 측정 대상이거든요.**

## 9:00 성능 측정 계획 (4분)

여기가 오늘 제일 하고 싶은 얘기입니다.

### 원칙 네 가지 (1분)

하나, **입력 세트는 한 번 만들고 고정합니다.** 중간에 바꾸면 이전 결과랑 비교가 깨져요.

둘, **한 주에 손잡이 하나만 바꿉니다.** 두 개를 동시에 바꾸면 뭐가 효과였는지 알 수가 없습니다.

셋, **조건 변경은 코드가 아니라 배포 파라미터로 합니다.**
같은 커밋에서 조건만 달리 배포해야 비교가 깨끗해요.

넷, **측정할 때마다 git tag를 남기고** 결과 CSV랑 1대1로 묶습니다.

### 트래픽 문제 해법 (1분)

아까 트래픽 얘기로 다시 돌아오면요.

실사용자를 기다리는 대신 **고정 입력 세트 80건**을 만들었습니다.
시나리오 20개 곱하기 턴깊이 네 가지. 이미 생성해서 레포에 넣어뒀습니다.

턴깊이가 독립변수고요. 매 측정마다 같은 세트를 같은 순서로 돌립니다.
이러면 **실트래픽보다 오히려 전후 비교가 깨끗합니다.** 변수가 하나니까요.

### 무엇을 기록하나 (1분)

> JSON 레코드 화면 공유

요청 한 건당 JSON 한 줄씩 남깁니다.
콜드스타트 여부, 턴 수, 히스토리 전략, 입력 토큰, 캐시된 토큰, 출력 토큰,
LLM 지연, 전체 지연, 메모리, 모델.

여기서 **cachedTokens가 제일 중요한 지표**입니다.
프롬프트 캐싱이 턴 누적 비용을 얼마나 눌러주는지가 5주차 결론이 될 거예요.

### 손잡이 (1분)

> 손잡이 표 화면 공유

손잡이는 여섯 개 잡아놨습니다.

히스토리를 전체 보내는 게 기준선이고요.
최근 N턴만 보내는 window, 오래된 턴을 요약으로 압축하는 summary.
이 셋이 서로 트레이드오프가 다릅니다.
**window는 토큰이 상수로 수렴하는 대신 맥락을 잃고,**
**summary는 맥락은 유지되는데 요약 호출 비용이 추가로 들어요.**

나머지는 프롬프트 캐싱, 모델 라우팅, Lambda 메모리입니다.
전부 코드가 아니라 SAM 파라미터로 빼놨습니다. 배포할 때 값만 바꾸면 되게요.

### 8주 뒤에 답하고 싶은 것 (30초)

네 가지에 숫자로 답하는 게 목표입니다.

10턴 쌓이면 1턴 대비 비용이 **몇 배**가 되는지.
프롬프트 캐싱이 그걸 **몇 퍼센트** 눌러주는지.
window랑 summary 중에 **비용 대비 효율**이 어느 쪽이 좋은지.
그리고 동시 요청을 올렸을 때 **어디서 먼저 무너지는지.**
Lambda 스로틀인지, OpenAI 429인지, 타임아웃인지.

지금까지 한 건 레포 구성이랑 측정 스크립트, 입력 세트 80건까지입니다.

솔직히 **아직 배포를 못 했습니다.**
AWS 계정도 아직 안 만들었고 SAM CLI도 설치 전이에요. 이번 주에 처리하겠습니다.

다음 주 목표는 네 개입니다.

먼저 AWS 계정이랑 **Budgets 알림부터** 설정하려고요.
6주차에 부하를 걸어야 하는데 가드레일 없이 하면 위험할 것 같아서요.

그다음 배포해서 응답하는 엔드포인트 확보하고,
80건으로 첫 측정 돌려서 숫자가 나오는지만 확인하고,

마지막으로 **턴깊이 1이랑 10의 입력 토큰 차이를 실측**해보려고 합니다.
선형으로 증가한다는 제 가설이 맞는지부터 확인해야죠.

## 예상 질문 대비

**"왜 29초예요?"**
> Lambda는 15분까지 돌 수 있는데 API Gateway가 29초에서 끊습니다.
> 그때 Lambda는 계속 실행 중이고 요금도 나가는데 클라이언트만 504를 받아요.
> 7주차에 Function URL로 바꿔서 비교해볼 생각입니다.

**"프롬프트 캐싱 조건이 뭔가요?"**
> 아직 정확히 확인 못 했습니다. 5주차 전에 문서 보고 정리해오겠습니다.

**"턴 수 말고 다른 변수는 없나요?"**
> 지금은 턴 수 하나로 고정했습니다. 변수를 늘리면 전후 비교가 흐려져서,
> 일단 하나로 가고 4주차 결과 보고 필요하면 추가하려고 합니다.

**"영어 품질은 어떻게 평가하나요?"**
> 이번 스터디 범위에서는 안 잽니다. 성능이 주제라 품질은 window/summary 전략이
> 맥락을 잃는지만 정성적으로 확인할 생각입니다. 솔직히 이건 아직 방법이 없습니다.
