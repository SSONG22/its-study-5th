# 잇츠 스터디 5기 — Codex기반 AI 성능 개선

> 2026.10.03 ~ 11.30 · 8주 · 서울 우먼잇츠 × OpenAI

## 프로젝트 — English Roleplay

상황을 고르고 영어로 대화하는 멀티턴 롤플레이 서비스.
**LLM 성능 측정을 먼저 설계하고, 그 위에 서비스를 올린** 프로젝트다.

## 이 프로젝트가 재려는 것

대화 턴이 쌓이면 히스토리를 매번 다시 보내야 해서 **입력 토큰이 선형으로 증가한다.**
비용과 지연이 턴 수에 비례해 올라간다. 이 증가를 누르는 손잡이들을 하나씩 바꿔가며
효과를 숫자로 비교한다.

| 손잡이 | 기대 | 대가 |
|---|---|---|
| 히스토리 전체 전달 (full) | 맥락 유지 | 토큰 선형 증가 |
| 최근 N턴만 (window) | 토큰 상수 수렴 | 맥락 손실 |
| 오래된 턴 요약 압축 (summary) | 토큰 절감 + 맥락 유지 | 요약 호출 비용 추가 |
| 프롬프트 캐싱 | 입력 토큰 과금 최대 90% 절감 | 프리픽스 1,024 토큰 이상 필요 |
| 모델 라우팅 | 비용 절감 | 품질 저하 |
| 스트리밍 | 체감 지연(TTFT) 감소 | 실제 지연은 그대로 |

## 왜 로컬부터인가

처음엔 AWS Lambda 기반으로 설계했다가 순서를 바꿨다.
실험 목록을 인프라 의존도로 나눠보니 **핵심 실험 8개가 전부 로컬에서 성립**했고,
인프라를 거치면 손잡이 하나 바꿀 때마다 배포해야 해서 실험 반복 속도가 떨어진다.

로컬에서 먼저 측정하고, 끝난 뒤 AWS 배포 여부를 판단한다. 아직 정하지 않았다.

로컬에서 측정하는 축: 토큰·캐싱·히스토리 전략·모델 라우팅·동시성(OpenAI rate limit)·스트리밍·백오프.
AWS 에 올려야 측정 가능한 축: 콜드 스타트, Lambda 메모리↔CPU, GB-초 비용, API Gateway 29초 제한.

## 구조

```
브라우저 (public/index.html)
    │  POST /api/chat   (stream:true 면 SSE)
    ▼
로컬 HTTP 서버 (Node 22, 내장 모듈만)
    │
    ├─ prompt.js        시스템 프롬프트 (~1,340 토큰, 캐시 프리픽스)
    ├─ conversation.js  히스토리 전략 full / window / summary
    ├─ llm.js           OpenAI 호출. 논스트리밍 + 스트리밍(TTFT 측정)
    └─ record.js        runs/{label}.jsonl 에 요청당 한 줄
```

### 시스템 프롬프트가 긴 이유

프롬프트 캐싱은 **프리픽스가 최소 1,024 토큰**이어야 걸린다.
짧은 프롬프트로는 `cachedTokens` 가 항상 0이라 캐싱 실험 자체가 성립하지 않는다.
실제 회화 서비스라면 역할·레벨·교정 정책·예시가 들어가므로 이 길이가 비현실적이지도 않다.

`SYSTEM_PROMPT` 블록은 **모든 요청에서 바이트 단위로 동일해야** 캐시가 적중한다.
날짜나 사용자 이름 같은 변동 값을 넣으면 캐시가 매번 깨진다.
그래서 시나리오는 블록 안이 아니라 **뒤에 별도 메시지로** 붙인다.

## 모델

**현재 사용 중** — Groq 무료 요금제

| 용도 | 모델 | 비고 |
|---|---|---|
| 주력 | `openai/gpt-oss-20b` | 추론 모델. 응답 토큰의 76~84% 가 추론 토큰 |
| 상위 | `openai/gpt-oss-120b` | 모델 비교용 |

계정마다 가용 모델이 다르다. `GET /openai/v1/models` 로 확인할 것.
문서에 production 으로 표기된 모델이 계정에 없을 수 있다.

**비교 예정** — OpenAI (유료)

| 모델 | 입력 / 캐시 / 출력 (1M 토큰당) | 캐시 할인 |
|---|---|---|
| `gpt-6-luna` | $0.10 / $0.01 / $0.50 | 90% |
| `gpt-6-sol` | $2.00 / $0.20 / $10.00 | 90% |
| `gpt-4.1-mini` | $0.40 / $0.10 / $1.60 | 75% |

마지막 모델은 할인율 비교용이다. 같은 재사용이라도 구형 모델은 할인폭이 작다.
공급자는 `.env` 의 `OPENAI_BASE_URL` 로 전환한다.

## 시작하기

사전 요구: Node.js 22+, OpenAI API 키

```bash
npm install
cp .env.example .env    # OPENAI_API_KEY 를 채운다. .env 는 커밋되지 않는다
npm start               # http://localhost:3000
```

브라우저에서 시나리오를 고르고 영어로 말을 걸면 된다.
화면 아래에 **턴마다 입력 토큰·캐시 적중·TTFT** 가 바로 표시된다.

## 측정

입력 세트 생성 (한 번만, 생성 후 커밋):

```bash
npm run gen     # 시나리오 20 × 턴깊이 1/3/5/10 = 80건
```

서버를 띄운 상태에서:

```bash
npm run measure -- --label w03-baseline
npm run load -- --label w06-concurrency
```

측정 레코드는 `runs/{RUN_LABEL}.jsonl` 에 쌓인다. 요청당 한 줄.

```json
{"label":"w03-baseline","historyTurns":10,"historyStrategy":"full",
 "inputTokens":1557,"cachedTokens":1344,"outputTokens":52,
 "ttftMs":310,"llmLatencyMs":1180,"totalLatencyMs":1195}
```

`cachedTokens` 가 이 프로젝트의 핵심 지표다.

## 측정 원칙

- **입력 세트는 한 번 만들고 고정한다.** 바꾸면 이전 결과와 비교가 깨진다
- **한 주에 손잡이 하나만 바꾼다.** 둘을 동시에 바꾸면 무엇이 효과였는지 알 수 없다
- **조건 변경은 코드가 아니라 환경변수로 한다**
- **측정할 때마다 git tag 를 남기고** `runs/{label}.jsonl` 과 1:1로 묶는다

```bash
git tag -a w4-window -m "히스토리 window(6턴), 입력토큰 1557→742, 캐시적중 0%"
```
